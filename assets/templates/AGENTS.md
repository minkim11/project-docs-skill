## 구현 경계

- 확정된 명세에 따른 코드 작성·테스트·버그 수정·리팩터링·코드 리뷰에서는 `docs/product/`와 `docs/archive/`, 과거 기획 메모를 읽거나 검색하지 않는다. 검색 대상은 ARCHITECTURE에 기록된 소스/테스트 루트와 현재 구현 문서로 지정한다. 프로젝트 전체 검색이 필요하면 금지 경로를 제외한다. 대화에 이미 있는 장기 계획도 현재 구현 요구로 취급하지 않는다.
- 전체 PRD는 사용자 요청이 제품 기획·PRD 작성/갱신·MVP 작성/범위 수정인 경우에만 읽는다. 문제 발견이나 기술 명세 수정만으로 이 범위를 확대하지 않는다.
- 현재 구현 기준은 [MVP](docs/implementation/MVP.md)다. 제외 범위를 구현하거나 미래 기능을 위한 API·필드·추상화를 선행 추가하지 않는다.
- Draft의 미정 표와 계약 충돌에서 현재 작업이 영향받는 REQ·초기화·검증 범위를 확인한다. 그 범위의 코드 변경/생성만 중단하고 문서·절·다른 값과 필요한 결정을 보고한다. 그 계약에 의존하지 않는 조사·검토·코드 작업은 계속할 수 있다. 전체 PRD를 찾아 임의로 해소하지 않는다.
- 제품 범위 변경이 필요하면 사용자에게 MVP 수정이 필요한 이유와 영향을 보고하고 범위를 정한 뒤 진행한다. 구현자가 스스로 작업 종류를 바꿔 PRD를 읽지 않는다. 명세의 동작을 유지하는 버그는 계약을 바꾸지 않고 수정한다. 요구사항이나 AC를 현재 코드에 맞춰 축소하지 않는다.

## 필요한 문서만 읽기

| 작업 | 읽기 대상 |
|---|---|
| 프로젝트 첫 구현·개발 환경 준비 | MVP의 목표·상태·범위, ARCHITECTURE의 기술스택·초기화 명세·패키지 구조, CONVENTIONS의 설정 계획·검사 명령 |
| 확정 명세에 따른 코드 작성·수정·리뷰 | MVP의 해당 REQ/AC, 대상 모듈 코드, CONVENTIONS의 적용 규칙·설정 경로 |
| 구조·모듈·의존성 변경 | ARCHITECTURE의 관련 부분; 결정 배경이 필요하면 ADR INDEX에서 해당 ADR 선택 |
| 데이터 저장 변경 | DATA_MODEL의 관련 엔티티·제약과 실제 스키마/마이그레이션 |
| HTTP API 구현·사용·계약 테스트 | openapi.yaml의 해당 operation과 참조 schema/security; 공개 API 변경은 명세를 먼저 수정 |
| 동작·타입·공개 계약을 바꾸지 않는 오타·포맷 수정 | 대상 파일, 해당 포맷/명명 설정·규칙 |

기술 문서: [아키텍처](docs/implementation/ARCHITECTURE.md), [코드 규칙](docs/implementation/CONVENTIONS.md).
선택 문서: {{실제 생성된 데이터 모델·OpenAPI·ADR 인덱스 링크만 유지}}.
처음에는 MVP의 목표·범위·상태를 확인하고, 작업에는 관련 요구사항과 필요한 기술 절만 읽는다. 모든 문서를 기본 로딩하지 않는다.

확정 명세에 따른 코드 작성·수정·리뷰에서는 외부 코드 스타일 가이드를 조회하지 않는다. CONVENTIONS의 도구 설정과 로컬 필수 규칙·예외를 따른다. 이 제한은 외부 스타일 가이드에 대한 것이며, 현재 API·프레임워크 사용법의 공식 문서 확인까지 금지하지 않는다. 스타일 기준의 새 결정이 필요하면 적용 대상을 보고하고 컨벤션 문서 수정으로 해소한다. 현재 적용되는 시스템·프로젝트 지침은 계속 준수한다.

## 초기 생성과 구현 인수

1. 먼저 대상의 소스·빌드 설정·기존 파일을 확인한다. 기존 프로젝트를 초기 생성기로 재생성하지 않는다. 새 프로젝트도 문서가 있으면 빈 폴더로 취급하지 않는다.
2. ARCHITECTURE의 초기화 명세에 확정된 생성 방법·버전·옵션·작업 위치를 그대로 사용한다. 버전·옵션이 지원되지 않거나 명세가 부족하면 영향받는 생성을 멈추고 보고한다. 기억에 의존해 다른 생성기·최신 버전·의존성을 고르지 않는다.
3. 골격 생성 시 기존 파일과 같은 경로가 생기면 파일별 차이를 확인한다. ARCHITECTURE에 명시한 병합·대체 대상만 변경하고, 그 외 문서·소스·도구 설정·Git 메타데이터를 보존한다. 충돌 없는 별도 임시 위치에서 생성한 뒤 지정 파일만 병합할 수 있다. 이 규칙은 초기 생성 시의 무조건 덮어쓰기를 막는 것이며 이후 요청된 코드 수정을 금지하지 않는다.
4. ARCHITECTURE에 확정된 아키텍처·모듈/역할별 경로·책임·의존 방향을 따른다. 생성 결과가 문서와 다르면 원인을 확인하고 명세 보완 후 진행한다. 기술스택이나 스킬 예시만 보고 다른 구조로 재선정하지 않는다.
5. CONVENTIONS에서 구현 시 추가로 표시한 도구 설정·명령을 준비하고, 정해진 최초 빌드·테스트·실행 확인을 수행한다. 미실행·환경 차단은 통과와 구분한다. IDE에서 열렸다는 사실만으로 검증 완료로 보고하지 않는다.
6. 준비가 끝나면 현재 MVP와 관련 데이터/API 계약에 따라 기능을 구현·검증한다. OpenAPI는 외부 계약의 기준이며 생성 코드나 구현 결과로 덮어쓰지 않는다. 필요한 명세 변경은 문서 작업에서 해소한다.

## 검증

실제 실행 명령과 완료 조건은 CONVENTIONS의 자동 검사 절 및 해당 MVP의 AC를 따른다. 실행하지 않은 검증을 통과로 보고하지 않는다. 구현 완료와 배포 가능 상태를 구분한다.

확정된 포맷·린트·타입 검사 중 변경에 필요한 검사를 실행하고 위반을 수정한다. 도구·설정이 아직 없으면 구현 준비 항목으로 다루고 적용·검증 완료라고 보고하지 않는다. 도구 검사 통과만으로 외부 스타일 가이드 전체를 준수했다고 주장하지 않는다.
