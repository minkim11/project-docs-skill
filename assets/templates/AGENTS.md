# 프로젝트 작업 지침

- 현재 MVP: [MVP](docs/v{{버전}}/MVP.md)

## 구현 경계

- 구현은 현재 MVP의 범위와 관련 기술 계약을 따른다. 미래 기능을 위한 UI·API·저장 필드·확장 구조를 선행 추가하지 않는다.
- 코드 작성·테스트·수정·리팩터링·리뷰에서는 `docs/product/`·다른 버전 MVP·과거 기획 메모를 읽거나 검색하지 않는다. 검색은 현재 MVP 파일, 공통 `docs/implementation/`, 아키텍처가 지정한 소스·테스트·설정 경로로 한정한다. `docs/`·`docs/v*/` 전체를 일괄 검색하지 않는다. 대화에 있는 장기 계획도 현재 요구로 취급하지 않는다.
- 전체 PRD는 제품 기획·PRD 갱신·MVP 작성/범위 수정 요청에서만 읽는다. 구현 중 누락 발견이나 기술 명세 검토·수정만으로 이 경계를 확대하지 않는다.
- 설계 미정·계약 충돌은 영향받는 작업만 멈추고 문서·절·서로 다른 값·필요한 결정을 보고한다. 코드를 기준으로 REQ/AC를 축소하거나 높은 버전 폴더로 현재 대상을 바꾸지 않는다.

## 작업별 읽기

| 기준 문서 | 읽는 작업 | 읽을 범위 |
|---|---|---|
| 현재 MVP | 동작 구현·수정·검증 | 해당 REQ/AC와 제외 범위 |
| [아키텍처](docs/implementation/ARCHITECTURE.md) | 초기화·구조·연동·실행·배포·설정 변경 | 관련 생성 선택값·구성 요소·의존 방향·통신·실행·배포 구조 |
| [컨벤션](docs/implementation/CONVENTIONS.md) | 코드 작성·수정·검사 | 적용 규칙·도구 설정·검사 명령 |
| [데이터 모델](docs/implementation/DATA_MODEL.md) | 저장·파일 입력 변경 | 관련 엔티티·입력 계약·불변조건과 스키마 |
| [OpenAPI](docs/implementation/openapi.yaml) | HTTP 구현·연동·계약 검사 | 대상 HTTP 작업과 적용되는 공통 정의 |
| [ADR 인덱스](docs/decisions/INDEX.md) | 설계 변경 이유 확인 | 해당 영역의 Accepted ADR만 선택 |

처음에는 현재 MVP의 목표·범위를 확인하고, 이후에는 위 표에서 작업에 필요한 절만 읽는다. 오타·포맷만 바꾸면 대상 파일과 해당 규칙만 읽는다. 문서의 링크를 재귀적으로 따라가며 다른 문서를 일괄 로딩하지 않는다.

OpenAPI는 operationId 또는 HTTP 메서드·경로로 대상을 찾고 해당 작업, 적용되는 공통 인증·HTTP 정책, 필요한 내부 `$ref` 정의만 읽는다. 중첩 참조는 계약 이해에 필요한 범위까지 확인하며 무관한 작업·components나 파일 전체를 기본으로 읽지 않는다.

공식 근거 링크는 선정 출처이며 기본 구현 읽기 대상이 아니다. 명세 부족·충돌·사용법 또는 버전 문제 확인이 필요할 때만 관련 공식 자료를 조회한다. 외부 코드 스타일 가이드는 컨벤션 선정·변경에서만 확인한다.

## 구현과 검증

1. 구현 요청 범위와 기존 파일을 먼저 확인한다. 기존 프로젝트를 생성기로 재생성하지 않고, 새 골격을 생성할 때도 기존 문서·파일을 보존하며 병합한다.
2. 아키텍처의 버전 제약·초기화 선택값·구조를 적용하고 컨벤션의 도구 설정을 반영한 뒤, 해당 REQ와 데이터/API 계약에 따라 구현한다. 공개 계약 변경은 명세를 먼저 수정하며 생성 결과나 현재 코드로 계약을 덮어쓰지 않는다.
3. 관련 AC와 컨벤션의 검사를 실행하고 위반을 수정·재검사한다. 실행한 검사와 미실행 사유는 작업 결과로 보고하고 명세에 실행 이력을 누적하지 않는다. 도구 통과를 제품 동작 전체나 외부 스타일 가이드 전체 준수로 확대하지 않는다.

개인 PC 경로·비밀값·일회성 요청과 대기 상태를 공유 문서에 남기지 않는다. 기존 데이터와 다른 프로젝트의 설정을 보존한다.
