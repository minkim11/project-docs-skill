## 구현 경계

- 코드 구현·테스트·버그 수정·리팩터링·코드 리뷰에서는 `docs/product/` 전체 PRD, 기획 메모, `docs/archive/`를 읽거나 검색하지 않는다. 광역 검색은 소스와 허용 문서 경로로 한정한다. 이미 대화에 포함된 장기 계획도 현재 요구사항으로 취급하지 않는다.
- 전체 PRD는 제품 기획·PRD 갱신·MVP 작성 및 범위 수정 문서 작업에서만 읽는다. 기술 문서 수정만으로 이 권한을 확대하지 않는다.
- 현재 구현 기준은 [MVP](docs/implementation/MVP.md)다. 제외 범위를 구현하거나 미래 기능을 위한 API·필드·추상화를 선행 추가하지 않는다.
- 명세가 `Draft`이거나 동작·권한·데이터 처리·외부 계약에 미정/충돌이 있으면 영향받는 구현을 멈추고 필요한 결정을 보고한다. 독립적으로 가능한 작업은 계속한다. 전체 PRD를 찾아 임의로 해소하지 않는다.
- 구현 중 발견한 제품 범위 변경은 MVP 문서 작업으로 전환해 합의한 뒤 진행한다. 기존 계약 안의 버그는 계약을 바꾸지 않고 수정한다. 명세를 코드에 맞춰 축소하지 않는다.

## 필요한 문서만 읽기

| 작업 | 읽기 대상 |
|---|---|
| 일반 구현 | MVP의 관련 REQ/AC, 관련 코드, CONVENTIONS의 해당 규칙 |
| 구조·모듈·의존성 변경 | ARCHITECTURE의 관련 부분; 결정 배경이 필요하면 ADR INDEX에서 해당 ADR 선택 |
| 데이터 저장 변경 | DATA_MODEL의 관련 엔티티·제약과 실제 스키마/마이그레이션 |
| HTTP API 구현·사용·계약 테스트 | openapi.yaml의 해당 operation과 참조 schema/security; 공개 API 변경은 명세를 먼저 수정 |
| 작은 오타·스타일 수정 | 대상 파일과 해당 규칙 |

기술 문서: [아키텍처](docs/implementation/ARCHITECTURE.md), [코드 규칙](docs/implementation/CONVENTIONS.md).
선택 문서: {{실제 생성된 데이터 모델·OpenAPI·ADR 인덱스 링크만 유지}}.
처음에는 MVP의 목표·범위·상태를 확인하고, 작업에는 관련 요구사항과 필요한 기술 절만 읽는다. 모든 문서를 기본 로딩하지 않는다.

## 검증

실제 실행 명령과 완료 조건은 CONVENTIONS의 검증 절 및 해당 MVP의 AC를 따른다. 실행하지 않은 검증을 통과로 보고하지 않는다. 구현 완료와 배포 가능 상태를 구분한다.
