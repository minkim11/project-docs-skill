# 문서 계약

## 기준 경로와 정보 소유

| 경로 | 이 문서가 소유하는 정보 | 다른 문서에서 하지 않을 일 |
|---|---|---|
| `docs/product/PRD.md` | 문제, 사용자, 전체 제품 경험, 장기 방향, 제품 판단의 맥락 | 구현자가 참고하도록 링크하지 않음 |
| `docs/implementation/MVP.md` | 현재 버전의 동작·업무 규칙·제외 범위·완료 기준 | 기술 문서에 요구사항 본문을 복제하지 않음 |
| `docs/implementation/ARCHITECTURE.md` | 현재 기술스택, 패키지 구조, 모듈 책임·경계·의존 방향 | 데이터 필드·API 형식을 반복하지 않음 |
| `docs/implementation/CONVENTIONS.md` | 프로젝트 고유 코드 규칙, 실제 검증 명령 | 린터·포매터 설정과 명령 정의를 복사하지 않고 위치 참조 |
| `docs/implementation/DATA_MODEL.md` | 저장 모델, 필드·관계·제약·인덱스의 의도 | API의 전송 모델을 DB 구조로 취급하지 않음 |
| `docs/implementation/openapi.yaml` | HTTP 요청·응답·인증·오류의 외부 계약 | 동일한 Markdown API 명세서를 만들지 않음 |
| `docs/decisions/NNNN-title.md` | 중요한 결정의 이유·대안·결과·재검토 조건 | 현행 설계 전체를 ADR에 복사하지 않음 |
| `AGENTS.md` | 읽기 규칙과 작업 진입점 | 문서 작성 절차나 전체 프로젝트 요약을 넣지 않음 |

제품 배경과 장기 방향은 전체 PRD에 남기고 현재 계약의 상세 내용은 MVP가 소유한다. PRD는 현재 기능을 개략적으로 설명하고 기획자용으로 MVP를 연결할 수 있다. 반대 방향으로 구현 문서가 전체 PRD를 읽으라고 연결하지 않는다.

같은 동작의 서로 다른 제약은 중복이 아니다. 예: MVP의 중복 저장 방지, 데이터 모델의 유일성 제약, OpenAPI의 중복 요청 응답은 각각 제품·저장·통신 관점의 계약이다. 각 문서에는 해당 관점만 작성하고 요구사항 ID로 연결한다. 최소한의 연결 설명은 허용하되 상세 본문·표를 복사하지 않는다.

## 버전과 식별자

- 현재 구현 문서의 경로는 고정한다. 버전마다 새 활성 폴더를 만들지 않는다.
- 첫 MVP는 `0.1`, 다음 범위 변경은 `0.2`처럼 증가시키는 것을 기본으로 한다. 기존 프로젝트 버전 정책이 있으면 그것을 따른다. API의 `info.version`은 API 계약 버전이므로 MVP와 반드시 같지는 않다.
- `MVP.md` 헤더에 버전, `Draft` 또는 `Ready`, 변경 요약을 기록한다. 관련 기술 문서에는 적용 MVP 버전을 표기한다. `Ready`는 사용자가 받아들인 범위와 구현에 필요한 결정이 명확하고 활성 범위를 막는 미정이 없는 상태다. 대화에서 이미 합의했다면 다시 승인을 요구하지 않는다.
- 과거 문서는 기본적으로 Git 이력을 사용한다. Git이 없으면 버전 보존이 안 된다는 점을 보고하고, 사용자가 요청할 때 이전 구현 문서 묶음만 `docs/archive/mvp-<version>/`에 보관한다. 보관본은 기본 읽기 대상에서 제외한다. 자동 커밋·저장소 생성·원격 게시를 하지 않는다.
- 기능 요구사항은 `REQ-001`, 검증 기준은 `AC-001`로 프로젝트 내에서 유일하게 부여한다. 같은 의미의 항목은 버전이 바뀌어도 ID를 유지한다. 의미가 바뀌면 기존 항목의 교체를 변경 요약에 기록하고 새 ID를 사용한다. 삭제한 ID는 재사용하지 않는다.
- ADR은 `0001-title.md`부터 증가시킨다. `INDEX.md`에는 ID, 제목, 상태, 관련 경로/영역, 대체 ADR만 둔다. 이전 결정을 대체할 때 기록을 지우지 않고 상태와 대체 관계를 갱신한다. 현재 유효한 설계는 아키텍처에 반영한다.

## 읽기와 변경 경계

- 구현에서는 전체 PRD, 보관본, 기획 메모를 읽지 않는다. 문서가 부족하면 필요한 결정만 보고하고, 제품 범위를 추측하거나 요구사항을 코드에 맞춰 변경하지 않는다.
- MVP 작성·범위 수정 요청에서만 전체 PRD의 해당 부분을 읽어 범위를 다시 정한다. 기술 명세만 바꾸는 요청으로 전체 PRD 읽기를 확장하지 않는다.
- 현재 요구사항을 구현하는 데 필요한 장기 제약은 현재 MVP/기술 문서에 명시적으로 승격한다. 제외한 미래 기능을 위한 필드·API·플러그인 구조를 미리 설계하지 않는다.
- 문서 작업에서 애플리케이션 소스를 확인하는 것은 허용한다. 실제 기술 선택·필드·인증·오류 처리를 확인하지 못했으면 확정으로 적지 않는다.
- 각 문서의 명시적 소유 범위를 기준으로 충돌을 보고한다. 모순을 발견해도 오래된 것처럼 보이는 한쪽을 임의로 고르지 않는다. 사용자가 요청한 문서 수정에서 영향을 받는 계약을 함께 갱신하고 변경을 요약한다.
- 스킬 버전이 바뀌어도 기존 프로젝트에 일괄 적용하지 않는다. 명시적인 갱신 요청에서 현행 결정을 보존해 병합한다.

## 데이터 모델

ERD는 관계의 시각적 보조다. 같은 문서에 필요한 필드 타입, null 허용, 키, 유일성, 삭제 규칙, 제약과 인덱스를 적는다. API 모델과 저장 모델이 다르면 경계에서의 변환 규칙만 설명한다. 권한·사용자 분리가 있으면 데이터 소유 기준도 명시한다.

구현 전에는 이 문서가 저장 설계의 기준이다. 구현 시 SQL/ORM/마이그레이션은 이 계약을 반영하고 차이를 검증해야 한다. 이미 상세 스키마가 코드에 있으면 긴 필드 표를 재작성하지 말고 정확한 스키마 경로·심볼을 참조하며 변경할 제약만 정의한다. ERD와 의도·불변조건은 유지한다. 문서와 스키마의 차이를 발견하면 어느 쪽을 고칠지 해소한 뒤 전달한다.

## OpenAPI: 명세 우선

- 기본 템플릿은 OpenAPI 3.1.0이다. 프로젝트 도구가 지원하는 버전을 확인하고 필요한 경우 합의된 버전으로 조정한다. 버전 변경을 위해 의존성을 설치하지 않는다.
- 확정된 활성 범위의 HTTP 작업만 작성한다. `paths: {}`는 시작 양식이지 구현 가능한 API 명세가 아니다.
- 각 operation에 유일한 `operationId`, 관련 `REQ`/`AC` ID(`x-requirements`), 입력 위치·필수 여부·스키마, 성공 응답, 필요한 실패 응답, 권한/데이터 소유 처리를 명시한다. 로그인 유무·인증 방식을 추측하지 않는다.
- 확정된 인증에 맞춰 `securitySchemes`와 `security`를 설정한다. `security: []`는 해당 작업의 공개 접근을 뜻하므로 무심코 채우지 않는다. 비밀값·실제 토큰은 넣지 않는다.
- 형식, enum, null 허용, 길이·범위, 페이지 처리, 멱등성, 오류 모델은 해당 동작에 필요한 항목만 정한다. 재사용 스키마는 `components`와 `$ref`로 연결하고 의미가 다른 저장 모델을 억지로 공유하지 않는다.
- OpenAPI 3.1의 null은 JSON Schema 타입으로 표현한다(예: `type: [string, 'null']`). 3.0용 `nullable`을 섞지 않는다. 예시가 있으면 스키마를 만족해야 한다.
- 서버 주소를 알 때만 `servers`를 추가한다. 계획만 있는 배포 URL이나 외부 API를 만들어 넣지 않는다.
- 동작·데이터·API 계약을 상호 검토하고 활성 API가 채워졌는지 확인한 뒤 구현에 넘긴다. 설치된 검증기를 사용해 구조·참조 검증을 실행하고, 없으면 미실행을 밝힌다. YAML 파싱 성공을 OpenAPI 의미 검증 통과라고 보고하지 않는다.
- 구현은 이 명세를 따르고 계약 테스트 등으로 차이를 확인한다. 코드 생성 결과는 파생물이다. 외부 계약 변경은 문서를 먼저 수정하고 구현·테스트를 맞춘다. 명세가 그대로인 구현 버그 수정마다 계약을 바꿀 필요는 없다.
