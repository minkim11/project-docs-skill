# 문서 계약

## 기준 경로와 정보 소유

| 경로 | 이 문서가 소유하는 정보 | 다른 문서에서 하지 않을 일 |
|---|---|---|
| `docs/product/PRD.md` | 제품 개요·사용자 문제, 핵심 사용자·여정, 제품 전체의 기능과 우선순위, 제품 범위·확장 방향, 판단 근거·참고 자료 | 현재 MVP·다음 버전의 상태를 관리하거나 버전별 업무 규칙·완료 기준을 복사하지 않음. 구현자가 참고하도록 링크하지 않음 |
| `docs/v<version>/MVP.md` | 해당 버전의 동작·업무 규칙·제외 범위·완료 기준 | 기술 문서에 요구사항 본문을 복제하지 않음 |
| `docs/implementation/ARCHITECTURE.md` | 전체 구성·경계, 기술스택, 텍스트 패키지 트리·책임·의존 방향, 통신·실행 구조, 현재 범위의 배포 설계, 간결한 초기화 선택값 | 설치·DB 준비·실행의 작업 순서와 명령 모음, 코드 규칙·검사 명령·저장 필드·HTTP 상세·ADR의 논거를 넣지 않음. 도식·표·본문으로 같은 설계를 반복하지 않음 |
| `docs/implementation/CONVENTIONS.md` | 스타일 기준, 도구 설정, 검사 범위·시점·명령, 비자동 필수 규칙과 예외 | 초기화·DB 준비·앱 사용 절차, AC 본문·테스트 매핑 표, API 오류 계약을 넣지 않음 |
| `docs/implementation/DATA_MODEL.md` | 저장 모델과 제약·불변조건, 저장에 연결되는 비HTTP 입력 계약, 저장·전송 모델의 변환 | API schema를 저장 필드 표로 복제하거나 DB 준비 명령을 넣지 않음 |
| `docs/implementation/openapi.yaml` | HTTP 요청·응답·인증·오류의 외부 계약 | 동일한 Markdown API 명세서를 만들지 않음 |
| `docs/decisions/NNNN-title.md` | 모듈/데이터 소유 경계·공개 계약·교체 비용이 큰 기술 선택의 이유·대안·결과·재검토 조건 | 현행 설계 전체를 ADR에 복사하지 않음 |
| `AGENTS.md` | 현재 대상 MVP 경로, 작업별 문서 탐색, 읽기 경계, 공통 구현·검증 지침 | 개별 기능의 범위·설계·명령, 일회성 요청과 대기 상태, 문서 작성 스킬의 절차를 복사하지 않음 |

제품 배경과 제품 전체의 기능·장기 방향은 전체 PRD에 남기고 버전별 계약의 상세 내용은 MVP가 소유한다. PRD의 기능 우선순위는 제품 전체의 중요도이며 특정 MVP의 포함 여부나 구현 순서를 뜻하지 않는다. PRD에는 비즈니스 목표·KPI, 프로젝트 일정·배포 계획을 기본 항목으로 두지 않는다. 현재 대상은 AGENTS에서만 지정하고, PRD에는 현재 버전 링크·목표 요약·다음 버전 목록을 요구하지 않는다. 제품 목적·사용자·요구·정책·방향이 달라질 때 해당 절을 갱신하며 MVP 추가·전환만으로 갱신하지 않는다. 구현 문서가 전체 PRD를 읽으라고 연결하지 않는다.

## 중복과 참조 규칙

- 각 결정·규칙·수치·명령·근거의 상세 정의는 위 소유 문서의 한 절에만 둔다. 같은 문서의 다른 절에서도 요약 표·본문·결론으로 재서술하지 않는다. 독자는 같은 변경을 여러 곳에 반영할 필요가 없어야 한다.
- 전체 문서 탐색은 AGENTS의 작업별 표에만 둔다. 각 문서에 전체 링크 목록·관련 문서 모음·공통 읽기 지침을 붙이지 않는다. AGENTS에서도 작업별 표와 별도의 문서 목록을 중복 생성하지 않는다.
- 다른 문서 참조는 현재 규칙의 상세 정의를 대체할 때만 사용한다. 문서명만 반복하는 링크 대신 대상 절·REQ/AC·operationId·스키마·ADR을 지정한다. 같은 대상을 반복 연결하거나 링크를 따라 다른 문서를 일괄 읽도록 하지 않는다. ADR 인덱스는 결정 기록만 탐색한다.
- 선정 근거는 선택을 정의한 위치에 한 번만 기록한다. 동일 출처 링크와 호환성 설명을 여러 절에 반복하지 않는다. ADR이 있으면 아키텍처에는 선택 결과와 ADR 식별자만 남기고 대안·절충 이유는 ADR에서만 설명한다. ADR이 불필요한 선택은 소유 문서에 필요한 이유를 짧게 적는다.
- MVP의 AC는 관찰할 결과를 정의한다. CONVENTIONS에는 검사 명령·테스트 탐색 규칙과 꼭 필요한 기술적 검사 방법만 두고 AC 본문이나 동일한 테스트 매핑 표를 만들지 않는다.
- MVP의 REQ는 사용자·운영자의 입력·명령·설정에 대해 앱이 보장할 동작이다. 개발자의 환경 준비·오류 조사·포트 탐색 절차는 구현 명세에 작성하지 않고, 데이터 보존·비밀값 취급 같은 공통 작업 수칙은 AGENTS에 둔다. 실제 DB 연동 등의 필수 검증 조건은 유지하되 작업 절차와 명령을 AC에 복사하지 않는다.
- 서로 다른 계약에 필요한 표현은 유지한다. MVP의 업무 동작, DB의 유일성 제약, API의 오류 응답은 각각 다른 관점이다. 실행 가능한 명령·스키마·AC에 필수 값이 재등장할 수는 있지만 주변 설명과 근거까지 복사하지 않는다. 줄이기 위해 요구사항·독립적인 계약·완료 기준을 없애지 않는다.

공유 명세의 경로는 프로젝트 상대 경로 또는 환경변수·PATH·Wrapper로 표현하며 개인 PC의 사용자명·홈·설치 경로를 넣지 않는다. 문서에는 선택한 계약·규칙·생성 옵션·검증 조건을 남기고, 파일 존재 여부·설치 확인·검사 실행 결과와 일회성 안내는 최종 보고에 둔다. 구현 전후로 계약이 같으면 본문도 유지한다. 설계 결정이 빠진 미정과 그 차단 영향은 문서에 남기되, 미실행 검사나 미생성 파일을 설계 미정으로 취급하지 않는다. 상태 보고용 문서를 별도로 만들지 않는다.

## 버전과 식별자

- MVP만 `docs/v0.1/MVP.md`, `docs/v0.2/MVP.md`처럼 버전별로 둔다. ARCHITECTURE·CONVENTIONS·DATA_MODEL·OpenAPI는 `docs/implementation/`에 공통 현행 문서 한 벌로 유지한다. PRD와 ADR도 기존 공통 경로를 유지한다. 버전 폴더에 공통 문서·스킬·AGENTS 복사본을 만들지 않는다.
- 현재 대상은 루트 AGENTS의 `- 현재 MVP: [MVP](docs/v<version>/MVP.md)` 한 줄로 명시한다. 링크에는 프로젝트 루트 기준 경로를 쓰고 앵커·쿼리는 붙이지 않는다. 버전 폴더의 `<version>`과 MVP 헤더의 버전을 일치시킨다. 최신 폴더나 수정일로 대상을 추측하지 않는다.
- 첫 MVP는 `0.1`, 다음 범위 변경은 `0.2`처럼 증가시키는 것을 기본으로 한다. 기존 프로젝트 버전 정책이 있으면 그것을 따른다. API의 `info.version`은 API 계약 버전이므로 MVP와 반드시 같지는 않다.
- `MVP.md` 헤더에 버전, `Draft` 또는 `Ready`, 변경 요약을 기록한다. 관련 기술 문서에는 적용 MVP 버전을 표기한다. `Ready`는 사용자가 수락했거나 선택을 위임한 범위에서 MVP를 확정했고, 현재 REQ/AC와 필요한 기술 계약이 명시되어 제품 동작·초기화·구현을 막는 미정이 없는 상태다. 이미 합의한 내용은 재승인을 요구하지 않는다. `Ready`는 앱 구현·검증 완료를 뜻하지 않는다.
- 새 프로젝트의 생성 방법·런타임/프레임워크 버전·생성 입력·활성 모듈 경로가 미정이면 해당 결정과 차단 영향을 기록한다. 필요한 설계·선택값이 확정되어 있으면 작업 명령 부재·파일 미생성·검사 미실행만으로 Draft로 내리지 않는다. 실제 생성·실행 여부는 최종 보고에서 구분한다.
- 미정은 결정할 내용, 영향받는 REQ/AC·문서, 차단 단계(제품 범위/기술 설계/초기화·구현/검증/배포), 독립적으로 진행 가능한 범위를 적는다. 활성 구현을 막으면 Draft로 둔다. 미래 기능이나 배포 전용 항목은 현재 구현을 막지 않는다는 근거를 명시하고 별도 미정으로 남길 수 있다.
- 다음 버전은 새 MVP 파일로 작성하고 이전 완료본은 당시 합의 기록으로 보존한다. 오타·명백한 기록 오류는 수정 사유를 남겨 정정할 수 있지만 완료본을 현재 코드에 맞춰 덮어쓰지 않는다. 공통 기술 문서는 현재 계약에 맞춰 갱신한다. 따라서 과거 MVP의 링크에서 열리는 공통 문서는 최신 기준이며 당시 설계의 스냅샷이 아니다. 공통 문서의 과거 내용은 Git 이력, 주요 설계 변경 이유는 ADR로 확인한다. Git이 없으면 공통 기술 문서의 이전 내용이 보존되지 않는다고 보고한다. 자동 커밋·저장소 생성·원격 게시·별도 archive 묶음 생성은 하지 않는다.
- 다음 버전 후보만 기획할 때는 AGENTS의 현재 대상과 공통 기술 문서를 유지하고 후보 MVP에 변경 필요 계약·미정의 영향을 기록한다. 요청에 현재 대상 전환이 포함되면 AGENTS의 현재 링크와 공통 기술 문서의 적용 MVP를 함께 갱신한다. Draft를 대상으로 전환해도 구현을 막는 미정은 그대로 차단으로 남는다. 폴더 생성만으로 구현 준비 완료라고 판정하지 않는다.
- 기능 요구사항은 `REQ-001`, 검증 기준은 `AC-001`로 부여하며 한 MVP 안에서 정의가 중복되지 않게 한다. 같은 요구를 유지하는 버전들에 같은 ID가 등장하는 것은 정상이다. 표현 정리나 같은 동작의 상세 보완은 ID를 유지한다. 사용자에게 보이는 동작·권한·성공 조건을 다른 요구로 교체하면 새 ID를 부여하고 변경 요약에 이전 ID의 교체를 기록한다. 폐기한 ID는 재사용하지 않으며 원본 이력/파일을 삭제하지 않는다. 새 ID 배정은 직전 MVP·변경 요약을 확인하고, 충돌 우려가 있으면 해당 과거 기록만 확인한다.
- ADR은 `0001-title.md`부터 증가시킨다. `INDEX.md`에는 ID, 제목, 상태, 관련 경로/영역, 대체 ADR만 둔다. 이전 결정을 대체할 때 기록을 지우지 않고 상태와 대체 관계를 갱신한다. 현재 유효한 설계는 아키텍처에 반영한다.
- `docs/decisions/INDEX.md`가 폴더 안내와 탐색 진입점 역할을 겸한다. 별도 README는 생성하지 않는다. 구현자는 현재 설계를 먼저 확인하고, 이유가 필요한 경우 인덱스에서 해당 영역의 ADR만 고른다.

ADR 대상은 모듈·데이터 소유 경계, 외부 공개 계약, 교체 시 데이터 이전이나 다수 모듈 수정이 필요한 기술 선택이다. 단순 파일명·포맷 옵션은 해당 문서에서만 관리한다. `Proposed`는 미확정 선택지, `Accepted`는 합의되었거나 위임 범위에서 확정한 결정, `Superseded`는 다른 ADR로 대체된 이력이다. Proposed나 Superseded를 현재 구현 지침으로 적용하지 않는다.

ADR 하나는 하나의 결정 질문만 다룬다. 같은 기능에 관한 내용이어도 독립적으로 선택·변경·대체하거나 재검토할 수 있으면 별도 ADR로 나눈다. 예를 들어 서버의 데이터 소유 경계와 스키마 변경 도구 선정은 독립된 결정이다. 서로의 전제인 경우 필요한 ADR 식별자만 참조하며 본문을 복사하지 않는다.

실제로 검토한 선택지와 각 선택지의 장점·단점·비용·한계를 같은 기준으로 명시한다. 결정 절에는 채택 후보와 다른 후보를 기각한 판단 기준을 적고, 표의 장단점은 반복하지 않는다. 사용자 지정 사항은 제약으로 구분하며 허구의 대안·검토 이력을 만들지 않는다. 재검토 조건은 해당 결정에만 연결한다.

기존 ADR을 분리·재구성할 때는 각 결정의 이관 위치를 확인한다. 새 ADR로 옮긴 결정, 현행 소유 문서에서 관리할 내용, 철회한 결정을 대체 관계에 구분하고 결정 자체가 바뀌었는지도 적는다. 전체를 Superseded로 표시하기 전에 누락된 유효 결정이 없는지 확인한다. 일부만 대체되면 기존 기록에 남는 유효 범위와 부분 대체 관계를 명시한다. 편집상 분리를 새 설계 변경으로 꾸미거나 이관 표를 채우려고 불필요한 ADR을 추가하지 않는다.

## 읽기와 변경 경계

- 코드 작성·테스트·수정·리팩터링·코드 리뷰는 AGENTS가 지정한 현재 MVP와 공통 기술 계약을 적용하는 작업이다. 이 작업에서는 전체 PRD·다른 버전의 MVP·보관본·기획 메모를 읽지 않는다. 검색은 선택한 MVP 파일과 공통 문서·관련 코드로 한정하고 `docs/` 전체를 검색하지 않는다. 미정·모순 발견 시 영향받는 범위를 보고하되 제품 범위를 추측하거나 요구사항을 코드에 맞춰 변경하지 않는다.
- 사용자 요청이 제품 기획·PRD 작성/갱신·MVP 작성/범위 수정일 때만 전체 PRD의 해당 절을 읽는다. 발견한 문제를 문서 작업이라고 부르는 것만으로 읽기 범위를 확대하지 않는다. 기술 명세 수정·구현 명세 검토는 현재 MVP와 관련 계약만 사용한다.
- 생성된 AGENTS에는 작업에 필요한 절만 읽고 내부 링크를 재귀적으로 탐색하지 않도록 명시한다. 공식 근거 링크는 일반 구현의 기본 읽기 대상에서 제외하고 명세 부족·충돌·사용법·버전 문제 확인에만 조회한다. 외부 스타일 가이드는 컨벤션 선정·변경에서만 읽는다. 이 읽기 지침을 다른 구현 문서에 반복하지 않는다.
- 현재 요구사항을 구현하는 데 필요한 장기 제약은 현재 MVP/기술 문서에 명시적으로 승격한다. 제외한 미래 기능을 위한 필드·API·플러그인 구조를 미리 설계하지 않는다.
- 문서 작업에서 애플리케이션 소스를 확인하는 것은 허용한다. 실제 기술 선택·필드·인증·오류 처리를 확인하지 못했으면 확정으로 적지 않는다.
- 충돌을 발견하면 문서/절, 서로 다른 값, 영향받는 REQ·초기화·구현을 제시한다. 파일 날짜나 코드에 이미 있다는 사실만으로 한쪽을 정답으로 고르지 않는다. 합의 또는 위임 범위 내 결정으로 해소한 뒤 그 결정을 소유하는 문서와 직접 연결된 참조만 갱신한다.
- 스킬 버전이 바뀌어도 기존 프로젝트에 일괄 적용하지 않는다. 명시적인 갱신 요청에서 현행 결정을 보존해 병합한다.
- 기존 `docs/implementation/MVP.md` 등의 경로를 새 구조로 옮기는 작업은 해당 프로젝트의 구조 변경 요청에서만 수행한다. 내용과 링크를 확인해 버전 경로로 이전하고 AGENTS와 이전 경로를 참조하는 문서의 링크를 갱신한다. PRD에 현재 버전 링크를 새로 추가하지 않는다. 스킬 업데이트만으로 기존 파일을 이동·삭제하지 않는다.

## 데이터 모델

데이터 저장이 현재 범위에 있을 때 데이터 모델을 작성한다. 관계형 DB는 엔티티 관계·필드 타입·null 허용·키·유일성·참조 삭제 규칙을 기록하고 실제 조회 조건이 요구하는 인덱스를 명시한다. 파일·문서형 저장은 해당 포맷·식별자·수명/갱신 규칙을 정의하며 관계형 테이블이나 ERD를 억지로 만들지 않는다. API와 저장 모델의 필드가 다르면 변환 지점과 차이만 적는다. 사용자/조직별 데이터가 있으면 소유자 식별 기준·접근 경계를 명시한다.

구현 전에는 이 문서가 저장 설계의 기준이다. 구현 시 SQL/ORM/마이그레이션은 이 계약을 반영하고 차이를 검증해야 한다. 이미 상세 스키마가 코드에 있으면 긴 필드 표를 재작성하지 말고 정확한 스키마 경로·심볼을 참조하며 변경할 제약만 정의한다. ERD와 의도·불변조건은 유지한다. 문서와 스키마의 차이를 발견하면 어느 쪽을 고칠지 해소한 뒤 전달한다.

## OpenAPI: 명세 우선

- 기본 템플릿은 OpenAPI 3.1.0이다. 프로젝트 도구가 지원하는 버전을 확인하고 필요한 경우 합의된 버전으로 조정한다. 버전 변경을 위해 의존성을 설치하지 않는다.
- 확정된 활성 범위의 HTTP 작업만 작성한다. `paths: {}`는 시작 양식이지 구현 가능한 API 명세가 아니다.
- 이 프로젝트가 제공하는 현재 범위의 HTTP 인터페이스를 명세한다. 호출하는 외부 서비스의 API는 공식 계약을 참조하고 그 API를 프로젝트 소유로 다시 정의하지 않는다. 비HTTP 인터페이스는 OpenAPI에 맞추려고 구조를 바꾸지 않는다.
- 각 operation에 유일한 `operationId`, 현재 MVP에 존재하는 REQ/AC ID 배열인 `x-requirements`, 입력 위치·필수 여부·스키마, 성공 응답을 기록한다. MVP에 정의된 입력 오류·권한/소유 위반·대상 부재·외부 실패가 해당 작업에서 발생할 수 있으면 그 응답도 정의한다. 로그인 유무·인증 방식을 추측하지 않는다.
- 확정된 인증에 맞춰 `securitySchemes`와 `security`를 설정한다. `security: []`는 해당 작업의 공개 접근을 뜻하므로 무심코 채우지 않는다. 비밀값·실제 토큰은 넣지 않는다.
- 입력/출력 값의 형식·enum·null 허용·길이/범위는 확정된 값의 제약으로 정의한다. 목록을 나눠 조회하면 정렬·페이지/커서·개수 제한을, 변경 요청의 재시도를 지원하면 중복 처리 규칙을 명시한다. 해당 동작이 없으면 그 기능을 새로 추가하지 않는다. 오류가 공통 형식이면 재사용 schema로 정의한다. `components`/`$ref`를 사용하되 전송/저장 모델의 의미가 다르면 하나로 강제하지 않는다.
- OpenAPI 3.1의 null은 JSON Schema 타입으로 표현한다(예: `type: [string, 'null']`). 3.0용 `nullable`을 섞지 않는다. 예시가 있으면 스키마를 만족해야 한다.
- 서버 주소를 알 때만 `servers`를 추가한다. 계획만 있는 배포 URL이나 외부 API를 만들어 넣지 않는다.
- 동작·데이터·API 계약을 상호 검토하고 활성 API가 채워졌는지 확인한 뒤 구현에 넘긴다. [번들 검사](validation.md)는 지원하는 기본 항목만 확인한다. 전체 OpenAPI 구조·참조 검증은 설치된 전용 검증기의 비수정 모드로 실행하고, 없으면 미실행을 밝힌다. YAML 파싱이나 번들 검사 성공을 전체 OpenAPI 의미 검증 통과라고 보고하지 않는다.
- 구현은 이 명세를 따르고 계약 테스트 등으로 차이를 확인한다. 코드 생성 결과는 파생물이다. 외부 계약 변경은 문서를 먼저 수정하고 구현·테스트를 맞춘다. 명세가 그대로인 구현 버그 수정마다 계약을 바꿀 필요는 없다.
