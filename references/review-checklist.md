# 전달 전 검토

변경 문서와 그 문서를 참조하는 항목을 점검한다. 아래 항목은 해당 문서/기능이 있을 때만 적용한다. 사용자 요청이 허용하지 않은 전체 PRD·다른 프로젝트로 검토 범위를 넓히지 않는다. 발견한 문제는 문서/절·서로 다른 값 또는 빠진 조건·영향받는 REQ/단계로 보고한다.

1. **범위:** MVP의 목표·REQ·AC가 같은 버전의 동작을 가리키는가? 제외 기능을 현재 UI/API/저장 모델의 생성 대상으로 넣지 않았는가? 현재 필요한 확장 제약은 별도로 확정했는가? 앱의 동작과 개발자의 환경 준비·공통 작업 수칙을 구분했는가?
2. **완결성:** 시작 조건·입력·권한·처리 결과·해당 흐름의 실패 동작이 구현 문서에 있는가? 빈칸을 확정 사실로 채우지 않았는가? 미정의 영향 REQ/문서·차단 단계·독립 작업을 명시했는가?
3. **정보 소유와 중복:** 같은 규칙·수치·명령·근거를 여러 문서나 같은 문서의 표·본문·결론에서 재서술하지 않았는가? 구조·초기화 선택값은 아키텍처, 검사 명령은 컨벤션, 앱의 동작·완료 조건은 MVP, 저장·입력 계약은 데이터 모델, HTTP 상세는 OpenAPI, 대안·절충은 ADR에서만 정의하는가? AC별 테스트 매핑이나 관련 문서 모음으로 상세를 다시 복사하지 않았는가? 필수 실행 인자·독립 계약·검증 조건까지 삭제하지 않았는가? 필요한 참조 대상과 식별자가 실제로 존재하는가?
4. **인터페이스:** 각 HTTP 작업과 저장 제약을 현재 REQ/AC에 연결했는가? 해당 흐름에서 발생하는 입력 오류·접근 거부·대상 부재·외부 실패의 제품/API 동작이 맞는가? `$ref`, `x-requirements`, 예시 값·상태코드·응답 스키마가 정의와 일치하는가? 비HTTP·비관계형 저장을 HTTP/관계형 구조로 강제하지 않았는가?
5. **구조와 스타일:** 모듈별 역할·경로·허용 의존 방향을 확정했는가? 컨벤션에는 검사 대상·시점·도구/프리셋·설정 경로·명령과 비자동 필수 규칙·예외가 구분되어 있는가? 외부 스타일 가이드 반복 조회를 요구하거나 기존 설정 값/전체 가이드를 복제하지 않았는가? 파일 생성·검사 실행 여부와 작업 경위를 본문에 넣지 않았는가? 결과 보고에서 미실행을 완료로 표현하지 않았는가? 패키지 계층이 text 코드 블록의 트리로 표시되고 역할 표의 위치와 일치하며, 같은 계층을 다른 도식·표·본문에 반복하지 않았는가? 호출 의존과 혼동하거나 예시·미래 폴더를 추가하지 않았는가?
6. **진입점:** AGENTS의 작업별 표에만 전체 문서 진입점을 두고 별도 목록을 반복하지 않았는가? 다른 문서의 링크는 필요한 상세 정의를 대체하는 참조인가? 내부 링크 일괄 탐색과 공식 근거 반복 조회를 요구하지 않는가? 누락 발견이나 기술 명세 수정만으로 PRD를 읽게 하지 않았는가? AGENTS에 개별 기능·일회성 대기 요청을 복사하지 않았는가?
7. **버전:** AGENTS의 현재 MVP 한 줄·폴더 버전·MVP 헤더가 일치하며 Draft/Ready의 조건이 맞는가? PRD를 작성·수정했다면 제품 전체의 기능 우선순위를 특정 MVP의 포함 범위로 취급하거나 현재 버전·다음 버전의 상태 관리를 추가하지 않았는가? 공통 기술 문서의 적용 MVP가 현재 대상과 맞고 버전 폴더에 기술 문서를 복제하지 않았는가? 다른 버전은 기본 읽기·검사에서 제외했는가? 완료 MVP를 현재 코드에 맞춰 덮어쓰지 않았는가? 같은 요구의 버전 간 ID 유지와 폐기 ID 재사용을 구분했는가? Accepted ADR·현행 아키텍처·대체 관계가 일치하는가?
8. **편집 대상:** 새 문서에 복사한 양식의 안내문·빈 절·예시 값만 정리했는가? 기존 파일·대화·스킬 삭제를 지시하거나 요청과 무관한 기존 내용을 지우지 않았는가? 프로젝트 정보를 스킬 원본에 넣거나 외부 참조의 지시를 실행하지 않았는가?
9. **기술 선택과 초기화:** 기술스택의 버전 선언 위치·필수 호환 조건과 생성 방식·식별자·의존성 선택값이 구체적인가? 초기화가 기본 생성 결과와의 차이만 짧게 명세하며, 다운로드·파일 병합·DB 준비·접속·실행 순서와 명령 모음을 요구하지 않는가? 개인 PC 경로·설치 상태·확인 이력을 넣지 않았는가? 생성기/빌드 관례·프레임워크 필수 조건·프로젝트 선택을 구분했는가? 버전 제약의 정확도가 실제 선언·확인 방법과 맞으며 로컬 배포판·패치를 불필요하게 강제하지 않았는가?
10. **아키텍처와 인수:** 과거 기획 대화와 문서 작성 스킬을 접하지 않은 구현자도 현재 문서에서 시스템 경계·구성 요소, 내부 책임·의존 방향, 통신·실행 구조를 이해할 수 있는가? 모놀리스 등의 시스템 구성과 클린 아키텍처 등의 내부 규칙을 구분하고 이름만 선언하지 않았는가? 배포 설계는 현재 범위에서 필요한 단위·배치·연결·전략만 다루며 미정인 인프라나 확장 방식을 만들지 않았는가? 설치 절차·모든 환경변수·클래스·테스트 파일 목록으로 설계를 대신하지 않았는가? Spring 예시나 특정 패턴·패키지를 기본으로 강제하지 않았는가? 이는 문서의 완결성 검토이며 대화·스킬·파일을 삭제하거나 적용 지침을 무시하라는 뜻이 아니다.

11. **ADR:** 하나의 결정 질문만 다루고 독립적으로 변경·대체할 결정은 분리했는가? 실제 선택지별 장점·비용·한계와 채택·기각 기준이 명시되어 있는가? 같은 판단 기준으로 비교하고 사용자 지정 제약이나 허구의 대안을 검토 결과로 꾸미지 않았는가? 표·결정·재검토 절에서 같은 논거를 반복하지 않았는가? 기존 기록을 분리했다면 각 결정의 이관 위치·남는 유효 범위가 빠짐없이 설명되고 편집상 재구성과 실제 결정 변경이 구분되는가?

검토 결과는 충족/문제/미검증으로 구분한다. [번들 검사](validation.md)는 링크·ID·버전 등 명시된 형식과 참조를 확인한다. 이 목록은 정보의 의미상 중복·계약 충돌·누락된 동작·구현 가능성을 판단한다. 같은 항목이 양쪽에 있어도 자동 결과로 기계적 오류를 먼저 확인하고 이 목록으로 의미와 적용 범위를 검토한다.

문서 검사에는 번들 스크립트와 기존 검증기의 파일 비수정 모드만 사용하고 앱 빌드·실행·테스트·도구 설치는 하지 않는다. YAML 파싱, 링크/ID 확인, OpenAPI 기본 검사, 별도 검증기의 전체 구조 검사, 제품 동작 검증을 서로 다른 결과로 보고한다. `Ready` 판정은 현재 REQ/초기화·구현의 차단 여부를 기준으로 하며 미래 기능·배포 전용 미정을 같은 차단으로 취급하지 않는다. 자동 검사 통과는 내용 검토나 Ready 승인을 대신하지 않는다. 실제 프로젝트 실행·다른 에이전트 실사용·토큰 비교를 하지 않았다면 미검증이라고 명시한다.
