# 패키지 구조 기본값

새 프로젝트에서 유형과 기술을 먼저 확정하고 한 가지 구조를 아키텍처에 고정한다. 프레임워크가 요구하는 라우트·설정·진입점 경로가 우선이다. 확정되지 않은 프레임워크를 가정해 코드를 만들지 않는다. 같은 유형·같은 기술에는 아래 책임 구분을 일관되게 매핑한다.

| 유형 | 경로 기본값과 책임 |
|---|---|
| 웹 UI + API | 프레임워크 기본 라우트, `src/features/<feature>/` 기능, `src/server/` 서버 전용 연결, `src/shared/` 실제 공통 코드, `tests/` 통합 검증 |
| API 서버 | 프레임워크 기본 진입점, `src/modules/<feature>/` 기능, `src/infrastructure/` 외부 연결, `src/shared/` 실제 공통 코드, `tests/` 통합 검증 |
| CLI/로컬 도구 | `src/commands/` 명령, `src/core/` 핵심 처리, `src/adapters/` 입출력, `tests/` 검증 |
| 라이브러리 | `src/` 공개 진입점과 내부 구현 모듈, `tests/` 검증 |
| 모바일/데스크톱 | 플랫폼 기본 진입점, `features/<feature>/` 화면·로직, 플랫폼 관례에 맞춘 저장/통신 연결, 테스트 기본 경로 |

위 경로는 언어·프레임워크에 별도 관례가 없을 때의 기본값이다. Python 패키지나 프레임워크 전용 경로가 있으면 그 구조로 일관되게 매핑한다. 기능 단위 테스트는 해당 생태계가 권장하는 인접 배치를 유지할 수 있다. 프레임워크가 이미 담당하는 계층을 두 번 만들지 않는다.

아키텍처에는 추상 계층명만 적지 말고 실제 선택한 경로와 책임, 허용하는 의존 방향을 짧은 트리/표로 적는다. 코드·패키지 생성은 하지 않는다. 선택한 기술에서 위 책임을 어느 경로에 둘지 기록하여 다음 문서 수정에서도 유지한다.

빈 `shared`, `utils`, `domain`, `repositories`, `interfaces` 계층을 관성적으로 추가하지 않는다. 현 MVP에 존재하는 책임만 경로로 지정한다. 공통화는 실제로 공유하는 코드가 있을 때, 멀티 패키지 구조는 별도 실행/배포/공유 요구가 있을 때 선택한다. 설명용 트리에 미래 기능을 넣지 않는다.

기존 프로젝트에서는 실제 구조를 따른다. 새 기본값을 적용하려면 구조 변경 자체가 요청 범위에 있어야 한다. 모듈 경계나 의존 방향을 바꾸는 의미 있는 예외는 ADR로 이유를 남긴다. 단순 파일명 선택마다 ADR을 만들지는 않는다.
