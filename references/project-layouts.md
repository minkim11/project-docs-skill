# 아키텍처와 프로젝트 구조

이 문서는 스킬의 문서 작성 지침이다. 초기화·시스템 구성·내부 구조·통신·실행·배포 설계를 정하거나 변경할 때 필요한 절만 읽는다. 구현자는 생성된 프로젝트의 ARCHITECTURE와 AGENTS를 따른다. 이 스킬은 애플리케이션 생성·의존성 설치·빌드를 실행하지 않는다.

## 1. 기존 상태와 기술 확정

- 대상 프로젝트의 루트 목록·빌드/의존성 파일·기존 명세를 확인해 소스 루트, Wrapper와 도구 설정 위치를 식별한다. 기존 소스가 있으면 현재 구조를 보존하며 프로젝트 전체 초기 생성기를 다시 실행하지 않는다. 새 모듈 생성/구조 전환이 요청 범위에 있으면 그 대상만 명세한다.
- 문서만 있는 디렉터리는 새 코드 골격을 생성할 수 있는 대상이지만, 빈 디렉터리는 아니다. 기존 파일 보존은 AGENTS의 공통 작업 지침을 따르고, 초기화에는 생성 대상을 바꾸는 예외만 적는다.
- 언어·런타임, 프레임워크, 빌드/패키지 도구, 패키지/모듈 이름, 실행 단위와 MVP에 필요한 직접 의존성을 확정한다. 사용자가 이미 정한 내용을 다시 묻지 않는다. 기술이 미정이면 경로·명령·버전을 임의로 확정하지 않고 관련 명세를 Draft로 둔다.
- 기술스택에는 선택 버전, 프로젝트 내 버전 선언 위치, 필수 호환 조건과 공식 근거만 적는다. 개인 PC의 설치·실행 경로 대신 프로젝트 상대 경로·PATH·환경변수·Wrapper를 사용한다. 공식 배포·호환성을 확인하고 로컬 설치·실행 상태와 구분하되, 확인 결과와 미검증 사유는 최종 보고에 둔다. 문서 작업에서 앱 생성·설치·빌드를 실행하지 않는다.
- 버전 제약의 범위는 사용자 요구·호환성·재현성으로 정한다. 특정 PC의 설치 버전이나 배포판을 그대로 필수 조건으로 승격하지 않는다. 벤더·패치까지 필요한 경우 그 이유와 선언·확인 방법을 정하고, 주요 버전만 선언하는 toolchain을 패치 고정으로 설명하지 않는다. 이미 명시적으로 요구된 고정 버전은 보존한다.

## 2. 기본 골격은 확인된 생성 방법으로 명세

프레임워크별 골격을 모델의 기억만으로 재작성하지 않는다. 선택한 버전에 대응하는 공식 생성기·공식 스타터를 우선 사용하도록 계획한다. 공식 생성기가 없거나 사용할 수 없으면 공식 최소 예제/문서를 근거로 골격과 핵심 설정을 명세한다. 확인되지 않은 대체 생성기를 조용히 선택하지 않는다.

새 골격 생성이 필요한 대상만 ARCHITECTURE의 초기화 절에 아래 선택값을 짧게 기록한다. 기존 프로젝트는 필요한 변경만 명세한다. 기술스택·패키지 트리에 이미 있는 값은 반복하지 않는다.

| 항목 | 기록할 내용 |
|---|---|
| 생성 방식 | 도구/서비스·스타터 이름과 공식 URL. 생성 도구 버전·고정 ref는 결과에 영향을 줄 때만 명시 |
| 생성 입력 | 프로젝트/패키지 식별자, 빌드 도구·패키징, 필요한 직접 의존성의 정확한 선택값. 버전은 기술스택 표를 기준으로 함 |
| 기본값과의 차이 | 생성 결과를 그대로 사용할 수 없을 때 변경할 설정·대상 경로만 명시 |

현재 MVP 요구·사용자 지정 제약·호환성 때문에 필요한 차이만 추가하고, 이를 충족하는 생성기 기본 설정은 유지한다. 구현·운영 복잡도를 줄인다는 이유만으로 의존성 관리나 런타임 조달 방식을 임의 변경하지 않는다. 여러 방식 중 선택하는 변경은 [문서 계약의 ADR 기준](document-contract.md#기술-결정과-adr)에 따라 별도 ADR로 기록하고 초기화에는 적용 결과와 ADR 식별자만 남긴다. 이미 선택 ID로 명세한 의존성은 기본 생성 결과가 충분하면 Gradle/Maven 좌표 표로 다시 열거하지 않고 추가·변경분만 명세한다.

`최신 버전`, `필요한 의존성`, `적절한 패키지 구조` 같은 표현만으로 넘기지 않는다. 생성 옵션의 버전 호환성·의존성 식별자는 해당 공식 문서/메타데이터에서 확인한다. 결정에 필요한 근거가 없으면 해당 선택과 차단 영향을 미정으로 남긴다. 확인 이력은 최종 보고에만 둔다.

다운로드·압축 해제·임시 폴더 정리·파일 병합·Wrapper 실행·DB 생성·접속 확인 등의 작업 순서와 명령 모음을 작성하지 않는다. 이를 다른 필수 문서로 옮겨 생성하지도 않는다. 사용자가 별도로 실행 안내를 요청한 경우에만 실제 설정·스크립트를 기준으로 README 등에 필요한 절차를 작성한다.

생성 도구의 기본값은 변할 수 있다. 버전 고정과 옵션 기록으로 변동을 줄이되, 서비스가 과거 옵션을 더는 지원하지 않으면 동일 재생성을 보장하지 않는다. 구현자가 다른 버전으로 대체하지 않고 문서 보완 사항으로 보고하도록 한다.

## 3. 생성된 골격과 내부 배치 규칙 구분

- **생성기/빌드 도구가 정하는 골격:** 소스 루트, 빌드 파일, 진입점, 리소스·테스트 위치 등. 선택한 생성 결과/공식 문서를 근거로 경로를 기록하고 이를 모두 프레임워크의 강제 조건이라고 부르지 않는다.
- **프레임워크 규칙:** 파일 기반 라우팅, 스캔 범위 등 동작에 실제 영향을 주는 조건. 어떤 경로·심볼·설정이 왜 필요한지 명시한다. 권장사항과 필수 조건을 구분한다.
- **프로젝트가 정하는 내부 배치:** 기능/계층/모듈 구분, 공통 코드, 외부 연결과 의존 방향. 요구사항과 제약에 따라 선정하고 실제 경로를 확정한다. 같은 기술스택이라는 이유만으로 아키텍처나 배치 방식을 동일하게 정하지 않는다.

### 구조 선정 시 확정할 결정

이 스킬은 기능별·계층별·헥사고날 등의 아키텍처나 패키지 배치를 기본으로 강제하지 않는다. 모놀리스 등의 시스템 구성, 클린 아키텍처 등의 내부 의존 규칙, 기능별·계층별 패키지 배치는 서로 다른 결정이다. 함께 적용할 수 있지만 패키지 이름만으로 아키텍처 규칙이 전달된다고 가정하지 않는다.

1. 기존 설계와 명시적인 사용자 선택을 먼저 확인한다. 기준이 없으면 MVP 흐름·업무 복잡도·데이터 소유·외부 연결·운영 제약을 검토하고 이를 충족하는 단순한 구조를 제안한다. 문서 예시에 나왔다는 이유를 선택 근거로 쓰지 않는다.
2. 별도 실행·배포 단위가 필요한지, 업무 책임을 어떤 모듈로 구분할지, 모듈 안의 코드를 어떤 기준으로 배치할지 각각 확정한다. 여러 기술 대안 중 선택한 결정은 위 문서 계약의 ADR 기준을 따른다. 아키텍처에는 선택 결과와 해당 ADR 식별자만 남기고 대안·절충 이유를 반복하지 않는다.
3. 프레임워크가 정한 라우트·화면·진입점 경로는 보존한다. 모듈·계층의 영문 식별자·배치·책임과 허용·금지 의존 방향을 ARCHITECTURE에 기록한다. 특정 REQ나 진입점 파일이 경계를 이해하는 데 필요하면 그 식별자만 추가하고 모든 클래스·기능 구현 순서를 미리 나열하지 않는다. 명명 규칙은 CONVENTIONS를 따른다.
4. 소스·테스트 루트는 생태계 관례와 선정한 모듈 책임에 맞추고 기본 관례와 다른 배치만 명시한다. 테스트 탐색·검사 명령은 CONVENTIONS에서 정의하며 AC별 매핑 표나 전체 테스트 파일 목록을 만들지 않는다.
5. 현재 REQ나 런타임/프레임워크 동작에 필요한 역할만 설계한다. 선택한 구조에 필요하지만 아직 구현되지 않은 포트/인터페이스는 목적과 소비 모듈을 명시할 수 있다. 소비자·요구사항·프레임워크 제약이 없는 미래 확장용 추상화나 빈 공통 폴더는 생성 대상으로 적지 않는다.
6. 패키지·디렉터리 계층은 text 코드 블록에서 `├──`, `│`, `└──`로 연결한 트리로 표시한다. 트리는 포함 관계만, 역할 표는 트리의 위치와 책임만 소유한다. 같은 계층을 Mermaid·전체 경로 목록·본문으로 반복하지 않는다. 시스템 흐름·호출 의존과 구분하고 사용자 예시의 도메인명이나 계층을 자동 채택하지 않는다.

구조를 아직 확정하지 못했으면 영향받는 부분을 미정으로 표시한다. 구현자는 다른 아키텍처를 새로 선정하지 않고 확정된 프로젝트 문서를 따른다. 일관성의 대상은 선정 절차·명세 형식과 확정된 계약의 유지이며, 모든 프로젝트에 같은 아키텍처를 적용하는 것이 아니다.

### Spring Boot + Java에 적용하는 예시

Spring은 초기화와 구조 결정의 구분을 설명하는 예시다. 아래 배치 사례는 선택지가 어떻게 명세되는지 보여줄 뿐이며, Spring 프로젝트에서도 자동 채택하지 않는다.

- 공식 생성 방식으로 Spring Initializr를 선택했다면 서비스 URL, Java·Boot 버전, Maven/Gradle, group/artifact/package, 패키징과 의존성 선택값을 명세한다. 버전·의존성 ID는 당시 메타데이터로 확인하며 이 예시에 숫자 기본값을 고정하지 않는다.
- Initializr가 만드는 빌드/소스 골격을 보존한다. Maven/Gradle의 기본 소스·리소스·테스트 경로를 Spring이 강제하는 패키지 이름으로 설명하지 않는다.
- 애플리케이션 클래스와 컴포넌트/엔티티의 스캔 관계를 실제 설정에 맞춰 명시한다. 상위 기본 패키지를 사용한다면 그 정확한 이름과 애플리케이션 클래스 경로를 기록한다.
- 추가 업무 코드는 해당 프로젝트에서 선정한 구조와 스캔 설정에 맞춘다. 예를 들어 기능별 배치를 선택하면 `member` 아래 관련 클래스를, 계층별 배치를 선택하면 `controller`·`service`·`repository` 아래 해당 역할을 둘 수 있다. 어느 배치도 이 예시만으로 확정하지 않는다. 포트·어댑터 구조 등 다른 선택도 요구사항에 따라 가능하다.
- 실제 패키지·모듈 경로와 스캔 설정의 관계를 ARCHITECTURE에 기록한다. Controller·Service·Repository는 역할 예시이며 항상 모두 필요한 구성 요소가 아니다. 실제 MVP에 없는 기능·역할을 생성 대상으로 적지 않는다.
- 문서에 기록된 빌드 Wrapper와 CONVENTIONS의 명령으로 초기 검증하도록 전달한다. IDE에서 프로젝트를 열 수 있다는 사실과 빌드/실행 검증 통과를 동일하게 취급하지 않는다.

공식 참고: [Spring Initializr](https://github.com/spring-io/initializr), [Spring Boot 구조 안내](https://docs.spring.io/spring-boot/reference/using/structuring-your-code.html). 작성 시 대상 버전에 맞는 근거를 확인하며 구현 중 매번 읽도록 요구하지 않는다.

## 4. 프로젝트 간 기준 재사용

다른 프로젝트나 과거 대화를 자동 수집·기억하지 않는다. 사용자가 지정하지 않은 로컬 프로젝트를 검색하지 않는다. 별도 기준이 없으면 위 절차로 프로젝트 요구에 맞는 구조를 선정한다.

추가 기준은 사용자가 제공한 구조 명세/템플릿·참조 프로젝트 또는 설치된 스킬에 명시적으로 등록된 기준 프로필만 사용한다. 프로필에는 적용 기술·버전·아키텍처 범위, 생성 옵션, 경로·책임·의존 방향, 이름·버전을 둔다. 현재는 고정 구조 프로필이 없다. 같은 기술스택이라도 요구사항과 선정한 아키텍처가 맞지 않는 프로필을 적용하지 않는다.

프로젝트에서 고른 구조를 자동으로 공통 기준으로 승격하지 않는다. 공통 기준 등록은 요청된 스킬 수정에서만 수행한다. 원본 수정만으로 설치본이나 기존 프로젝트가 갱신되지는 않는다.

## 5. 구현 인수에 필요한 결과

ARCHITECTURE의 각 절은 다음 관점만 소유한다. 필요한 관점만 작성하고 표·도식·본문으로 같은 사실을 재서술하지 않는다.

- **전체 구성:** 시스템 경계와 구성 요소의 역할·데이터 소유. 전체 구조도는 필요할 때만 사용한다.
- **내부 구조:** 패키지 트리, 모듈·계층의 책임, 허용·금지하는 의존 방향과 외부 기술 접근 경계.
- **통신과 흐름:** HTTP·내부 호출·이벤트 등의 연결 방식, 동기·비동기 여부, 대표 처리 흐름과 트랜잭션·일관성 경계. 업무 규칙·DB 필드·API 상세는 복사하지 않는다.
- **실행 구조:** 서버·워커·배치의 진입점과 수명주기·실행 모드 관계. 전체 환경변수 목록 대신 설계에 영향을 주는 설정만 기록한다. 앱이 보장할 인자·입력·종료 동작의 상세는 MVP나 DATA_MODEL의 소유 절을 참조한다.
- **배포 구성:** 현재 범위의 배포 단위·배치·연결 경계. 갱신·롤백·확장 방식은 필요하고 결정된 것만 남긴다. 배포 제외 시 절을 생략하고 미래 배포 미정만으로 현재 구현을 막지 않는다.
- **제약:** 앞 절에 없는 보안·성능·가용성 조건 중 설계에 영향을 주는 것만 추가한다. 선택의 대안·트레이드오프는 ADR에 두고 초기화는 위의 짧은 선택값만 남긴다.

DB가 어디서 실행되고 누가 접근하는지, 스키마 변경을 어떻게 관리하는지는 필요한 설계다. DB 이름·계정·접속 값과 테스트 대상 확인은 [환경별 연결 설정](document-contract.md#환경별-연결-설정)을 따른다. DB 생성·계정 발급·접속 오류 조사 순서는 설계에 포함하지 않는다. AGENTS에는 작업별 문서 표와 공통 구현 지침만 두고 이 작성 지침을 복제하지 않는다.

구현자는 기존 상태 확인 → 명세대로 골격 생성/보존 병합 → 도구 설정 → 최초 빌드·테스트/실행 확인 → MVP 기능 구현 순서로 진행한다. 실제 생성 결과가 문서와 다르면 원인을 보고하고 계약을 해소한다. 버전·생성기·모듈 경계·패키지 경로를 임의 대체하지 않는다. 중요한 구조 변경은 ADR로 기록한다.
